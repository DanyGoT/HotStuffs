* Overview

Two Byzantine fault-tolerant consensus protocols in Go, built from the papers
rather than ported from an existing implementation, talking over [[4][Gorums]].

A group of =n= replicas agrees on an ever-growing log of commands, and keeps
agreeing while up to =f= of them are crashed, slow, or actively lying, where
=n = 3f + 1=. Four replicas tolerate one liar.

** The two protocols

| package      | protocol         | commits on          | status                |
|--------------+------------------+---------------------+-----------------------|
| =diem/=      | DiemBFT v4       | a contiguous 2-chain | the live one         |
| =consensus/= | Chained HotStuff | a 3-chain            | kept as the baseline |

=diem/= follows the DiemBFT v4 pseudocode (paper §3), one file per module of
the paper. It is where new work goes. =consensus/= came first and stays put, so
the report has something to compare against; it is not being extended.

** What a replica does, in a loop

#+begin_example
  the leader of this round bundles commands into a block and broadcasts it
      |
  everyone checks the block and votes for it, if their safety rules allow
      |
  the next leader collects a quorum of votes into a certificate (a QC)
      |
  a QC over two rounds in a row means the older block can never be undone
      |
  -> commit it, and the round advances
#+end_example

If a round produces no block — a crashed or silent leader — replicas time out,
and a quorum of timeouts forms a *timeout certificate* that lets the next
leader carry on without the missing round.

** How a message travels

The path from the network to the protocol and back is deliberately short:

#+begin_example
  gRPC/Gorums -> decode -> VERIFY -> queue -> Core.Step -> Transport -> out
                            |                    |
                  every signature checked   pure state machine:
                  here, on the handler      one goroutine, no locks,
                  goroutine. Anything       no crypto, no wire types
                  that fails is dropped
                  and never reaches Core.
#+end_example

The rule is *authenticate at the edge, authorise by state in the loop*. By the
time a message reaches =Core=, it is known to be genuinely signed; =Core= only
decides whether it is welcome given what the replica currently believes.

Interfaces exist only where there is genuinely more than one implementation.
=diem/= declares exactly one (=Transport=, which has a real one and a test one).
Everything else is a concrete type, because an interface with a single
implementation is a hop to step through while reading, and buys nothing.

** Running it

Four replicas in one process for ten seconds:

#+begin_src sh
go run ./cmd/hotstuff -protocol diem -local 4 -time 10s -payload 32 -workers 4
#+end_src

Four separate processes over TCP — the same code path, one per terminal, after
writing a key pair per replica:

#+begin_src sh
go run ./cmd/hotstuff -gen-keys -keys ./keys \
  -remotes 127.0.0.1:20001,127.0.0.1:20002,127.0.0.1:20003,127.0.0.1:20004

go run ./cmd/hotstuff -protocol diem -self 127.0.0.1:20001 \
  -remotes 127.0.0.1:20001,127.0.0.1:20002,127.0.0.1:20003,127.0.0.1:20004 \
  -keys ./keys -time 15s
#+end_src

Each replica prints how many blocks it committed; the =-local= runs also check
that every replica's log agrees over the prefix they share.

=make test= runs everything, =make race= under the race detector, and
=make check-deps= enforces the layering rules described below. =make proto=
regenerates the protobuf and needs =nix develop= for =protoc=.

** Where to look first

- =diem/core.go= — the event loop; the whole protocol surface is one =switch=
- =diem/safety.go= — the rules that decide whether voting is safe
- =diem/verify.go= — everything checked before a message is let in
- =.claude/notes/diembft-pseudocode.md= — the paper's pseudocode, transcribed

* Codebase Map

Layering runs leaf to root: =hotstuff= depends on nothing but the standard
library, =consensus= holds the protocol, =network= is the only package allowed
to know that Gorums exists, and =replica= wires them together. =make check-deps=
enforces this mechanically.

** Where the protocol actually lives

The algorithm is three functions in =consensus/rules.go=; everything else is
plumbing around them.

- Vote rule — =consensus/rules.go:38-44=, called from =consensus/core.go:182=
- Propose rule — =consensus/rules.go:48-54=, reached via =pacemaker.go:26=
- Commit rule — =consensus/rules.go:64-83=, the three-chain walk
- Quorum certificate formation — =consensus/core.go:204-223=
- View change — =consensus/pacemaker.go= in full; timer at lines 91-102
- Block storage — =blockchain/store.go:46-131=
- Safety, enforced — the lock check in =rules.go:38-44= and =pacemaker.go:53-61=
- Safety, checked — =simnet/safety.go:28-79=, as a test oracle

** Where the DiemBFT protocol lives

For DiemBFT the algorithm is the =Safety= module plus the commit rule;
everything else is plumbing around them.

- The whole protocol surface — =diem/core.go:153=, =Core.Step=, one switch over
  a sealed event set, so the cases are exhaustive
- Voting rules — =diem/safety.go:63= =safeToVote= and =:77= =safeToTimeout=,
  both resting on =consecutive= at =:49=
- Commit rule — =diem/safety.go:97= =commitStateIDCandidate=: a block whose
  round directly follows its parent's carries the parent's speculated state, so
  the quorum certifying the block also certifies that commit. That is the
  2-chain rule, against Chained HotStuff's 3-chain
- Certificate formation — =diem/blocktree.go=, =ProcessVote=
- Round change — =diem/pacemaker.go= in full
- Leader selection — =diem/leader.go=, round-robin plus the reputation scheme
- Checked before anything touches state — =diem/verify.go=

Verification is split by the rule *authenticate at the edge, authorise by state
in the loop*. Signatures, quorum sizes, certificate well-formedness and signer
ordering are checked in =diemnet/server.go=, off the consensus goroutine, and
anything that fails is dropped before it is queued. What stays in =Core= is
what depends on this replica's current beliefs: whether the sender leads this
round, and whether the message is too far ahead to buffer. The leader check
cannot move to the edge at all, because =LeaderElection= has a reputation path
keyed on committed blocks, so the leader is a function of protocol state.

=diem/core.go= therefore holds exactly one crypto call — =Sign=, when this
replica proposes. =Safety= re-verifies what it is about to sign over, which is
deliberate: it holds the private key and is the one module assumed to survive
the rest being compromised.

=diem= declares exactly one interface, =Transport=. The ledger, the mempool,
the block tree and the backoff policy are concrete types, called directly — an
interface with a single implementation is a hop to step through while reading
and buys nothing.

** How we use Gorums

=proto/hotstuffpb/hotstuff.proto:33-44= defines one service with four RPCs:

#+begin_example
rpc Propose(Proposal)   returns (Empty) { option (gorums.multicast)  = true; }
rpc Vote(VoteMsg)       returns (Empty) { option (gorums.multicast)  = true; }
rpc Timeout(TimeoutMsg) returns (Empty) { option (gorums.multicast)  = true; }
rpc Fetch(BlockHash)    returns (Block) { option (gorums.quorumcall) = true; }
#+end_example

Three multicasts and one quorum call. Two choices there are worth explaining.

Votes are multicast rather than unicast to the next leader, which is a
deliberate divergence from the paper. Sending a vote only to the leader of the
next view makes that leader the sole collector for the view, so a crashed
replica that is both a leader and the preceding view's collector stalls
commits. Here every replica multicasts its vote and every replica accumulates
independently (=consensus/core.go:197-223=). The reasoning is recorded at
=hotstuff/seams.go:20-24= and again above the RPC in the .proto.

Fetch is the one real quorum call, used for backfilling a missing ancestor.
It takes the first reply rather than waiting for a quorum
(=network/gorums.go:189=), which is safe only because blocks are
content-addressed: the reply is re-hashed and checked against the request at
=network/gorums.go:199-204=. One correct answer is therefore enough, whoever
sends it.

The node configuration is built in =network/gorums.go:78-119=, registering peers
with =gorums.WithPeers= / =gorums.WithNodes=. The replica registers *itself* as a
peer, so a leader's own proposal comes back through the ordinary inbound path
instead of taking a shortcut into the state machine — one code path, not two.

Conversion between domain and protobuf types lives entirely in
=network/wire.go=. Inbound, it never trusts a hash off the wire: blocks are
rebuilt with =hotstuff.NewBlock= and rehashed (=wire.go:191-193=).

** How DiemBFT uses Gorums

Gorums allows one service per =.proto= file, so DiemBFT gets its own.
=proto/diempb/diem.proto:107-123= defines three RPCs, and deliberately no
fourth:

#+begin_example
rpc Proposal(ProposalMsg) returns (Empty) { option (gorums.multicast) = true; }
rpc Vote(VoteMsg)         returns (Empty) { option (gorums.unicast)   = true; }
rpc Timeout(TimeoutMsg)   returns (Empty) { option (gorums.multicast) = true; }
#+end_example

Votes are *unicast*, unlike the HotStuff service above. DiemBFT 3.1 sends a
vote to the leader of the next round alone, because that leader is the only
replica that will propose over the certificate. The paper's mapping is kept
here, which is what makes the two transports comparable.

There is no =Fetch=. Section 3 specifies no block-sync, and none was added, so
a replica that misses an ancestor cannot speculate and declines to vote until
the chain catches up with it. =Safety.DeclinedMissingAncestor()= counts exactly
those declines, which is what makes the gap measurable rather than
hypothetical — and it is not rare. Message *reordering alone*, with nothing
dropped and nothing malformed, is enough to trigger it: Gorums gives per-sender
FIFO, but rounds rotate leaders, so consecutive proposals arrive from different
senders on different handler goroutines.

Certificate signature sets travel in strictly increasing signer order. A block
id covers the signature slice byte for byte, so permuting it would change the
id on the receiver and fork the chain; =diemnet/wire.go= preserves the order
and =diem/verify.go= rejects any certificate that arrives out of it.

** The layering rule

=make check-deps= (Makefile:30-36) enforces four things:

1. =hotstuff= may import nothing outside the standard library.
2. =hotstuff=, =crypto=, =blockchain= and =consensus= may not import
   =hotstuffpb= or =relab/gorums=. Gorums stays behind the =Transport= seam.
3. =hotstuff= and =consensus= may not contain a =go= statement — the protocol
   core does not spawn goroutines.
4. No package may use =reflect=.

The practical effect of (2) is that the protocol can be tested, and the event
loop replaced, without a network or a wire format anywhere in sight — which is
what =simnet= relies on.
