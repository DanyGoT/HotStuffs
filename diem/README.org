#+title: DiemBFT v4

An implementation of the DiemBFT v4 pseudocode, section 3 of the paper. It
commits on a contiguous 2-chain. =PSEUDOCODE.org= maps each procedure onto the
code.

* The tree

The package works directly on the generated =diempb= messages, which are
read-only once built. Rounds are =uint64=, replica ids =uint32=, hashes
32-byte slices.

One file per module of the paper's section 3.

#+begin_example
diem/
  core.go          3.1 Main — the event loop; the whole surface is one switch
  ledger.go        3.2 Ledger — speculative execution over a branching state
  blocktree.go     3.3 Block-tree — pending blocks, vote buckets, QC formation
  safety.go        3.4 Safety — the voting rules and the only key holder
  pacemaker.go     3.5 Pacemaker — round advance, timeouts, TC formation
  mempool.go       3.6 MemPool — where a leader's payload comes from
  leader.go        3.7 LeaderElection — round-robin and the reputation scheme
  verify.go        everything checked before a message is let into the loop
  events.go        the sealed event set and the bounded Queue
  loop.go          the event loop driver — Run, Tick, Step over the queue
  types.go         NewBlock and the small helpers over the diempb messages:
                   QCRound, Commits, MaxHighQCRound, well-formedness
  seams.go         Transport, Crypto and Clock: what the core plugs into
  quorum.go        Faulty(n), QuorumSize(n), QuorumReached
  hash.go          domain-separated digests, over plain byte slices
  genesis.go       the fixed genesis block and its certificate
  sim_test.go      the deterministic multi-replica harness
  fakes_test.go    stand-in signer and hand-driven clock for the tests

diemnet/           the Gorums layer; may import Gorums and protobuf
  gorums.go        the Transport: outbound calls, bounded dropping send queue
  server.go        inbound handlers; verifies at the edge, then enqueues the
                   received message as it is

proto/diempb/
  diem.proto       the wire messages and the Gorums service
  *.pb.go          generated by protoc-gen-go and protoc-gen-gorums

replica/replica.go wires Core + Loop + Transport; owns the lifecycle
#+end_example

* Where the protocol lives

The algorithm is the =Safety= module plus the commit rule; everything else is
plumbing around them.

- The whole protocol surface — =core.go:151=, =Core.Step=, one switch over a
  sealed event set, so the cases are exhaustive
- Voting rules — =safety.go:63= =safeToVote= and =:77= =safeToTimeout=, both
  resting on =consecutive= at =:49=
- Commit rule — =safety.go:97= =commitStateIDCandidate=: a block whose round
  directly follows its parent's carries the parent's speculated state, so the
  quorum certifying the block also certifies that commit. That is the 2-chain
  rule
- Certificate formation — =blocktree.go=, =ProcessVote=
- Round change — =pacemaker.go= in full
- Leader selection — =leader.go=, round-robin plus the reputation scheme
- Checked before anything touches state — =verify.go=

* Verification

The rule is *authenticate at the edge, authorise by state in the loop.*

Signatures, quorum sizes, certificate well-formedness and signer ordering are
checked by =Verifier=, called from =diemnet/server.go= on the handler
goroutine, and anything that
fails is dropped before it is queued. What stays in =Core= is what depends on
this replica's current beliefs: whether the sender leads this round, and
whether the message is too far ahead to buffer.

The leader check cannot move to the edge at all, because =LeaderElection= has a
reputation path keyed on committed blocks, so the leader is a function of
protocol state.

=core.go= therefore holds exactly one crypto call — =Sign=, when this replica
proposes. =Safety= re-verifies what it is about to sign over, which is
deliberate: it holds the private key and is the one module assumed to survive
the rest being compromised.

* Interfaces

This package declares three, all in =seams.go=, and each has a real
implementation and a test one: =Transport= (=diemnet= and the sim's in-memory
network) is the hand-off out of the consensus goroutine, =Crypto= (=crypto= and
=testSigner=) signs and verifies digests as plain bytes, with the signer id as an
argument — it knows nothing of the message types, and counting a quorum is
=QuorumReached= in =diem=, and =Clock= (=SystemClock= and =fakeClock=)
arms the round timer.

The ledger, the mempool, the block tree and the backoff policy are concrete
types, called directly. An interface with a single implementation is a hop to
step through while reading and buys nothing.

* How it uses Gorums

=proto/diempb/diem.proto= defines three RPCs, and deliberately no
fourth:

#+begin_example
rpc Proposal(ProposalMsg) returns (Empty) { option (gorums.multicast) = true; }
rpc Vote(VoteMsg)         returns (Empty) { option (gorums.unicast)   = true; }
rpc Timeout(TimeoutMsg)   returns (Empty) { option (gorums.multicast) = true; }
#+end_example

Votes are *unicast*: DiemBFT 3.1 sends a vote to the leader of the next round
alone, because that leader is the only replica that will propose over the
certificate.

There is no =Fetch=. Section 3 specifies no block-sync, and none was added, so
a replica that misses an ancestor cannot speculate and declines to vote until
the chain catches up with it. =Safety.DeclinedMissingAncestor()= counts exactly
those declines, which is what makes the gap measurable rather than
hypothetical.

It is not rare. Message *reordering alone*, with nothing dropped and nothing
malformed, is enough to trigger it: Gorums gives per-sender FIFO, but rounds
rotate leaders, so consecutive proposals arrive from different senders on
different handler goroutines. Seeing round r+1's certificate before round r's
proposal is enough to strand the replica.

Certificate signature sets travel in strictly increasing signer order. A block
id covers the signature slice byte for byte, so permuting it would change the
id on the receiver and fork the chain; =verify.go= rejects any certificate
that arrives out of it.

No digest from the wire is trusted until the edge has recomputed it. The
=Verifier= requires every hash field to be exactly 32 bytes, and recomputes a
proposal's block id once: the proposer stamps it in =Block.id= because hashing
the payload is expensive, and after =VerifyProposal= the core reads =GetId()=
instead of hashing again.

* Running it

Four replicas in one process:

#+begin_src sh
go run ./cmd/diem -local 4 -time 10s -payload 32 -workers 4
#+end_src

Each replica prints how many blocks it committed, how many votes it declined
for a missing ancestor, and how many messages the edge rejected. The =-local=
runs also check that every replica's log agrees over the prefix they share.
